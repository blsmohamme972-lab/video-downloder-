## What changed

Eligible ordinary YouTube HTTP/HTTPS formats now use up to eight parallel requests, each bounded to 8 MiB. The app preserves the exact selected video/audio format IDs and never uses a lower resolution or lossy re-encode to improve transfer speed. Native manifest downloaders and unknown-size formats retain their existing paths.

Verified ranges are appended in order to the same contiguous `.part` file. A 64 KiB overlap check compares the existing prefix with the refreshed source. Response status, range, total size and body length are validated. Known-size fallback also checks final length so a short HTTP error body cannot be published as completed media.

The Java owner and Python supervisor now stop and reap the download process group before pause/resume/delete can release its ownership. A separate deadline handles stalled supervisors, and unexpected supervisor exit also cleans up remaining descendants. Startup and engine updates validate the adapter before accepting the extractor.

The UI displays fractional progress such as 0.5% and explains that parallel transfer preserves selected quality.

This is a controlled transfer benchmark, not a measured speed increase on the user's Wi-Fi or on YouTube. It demonstrates the benefit when individual requests are limited and aggregate bandwidth is available. Timing is reported rather than asserted in CI because shared-runner performance varies.

## Live-source and device limits

A live YouTube metadata check succeeded for the public upstream Big Buck Bunny example. Direct CDN range requests then returned HTTP 416. A small stock-downloader comparison returned only 195 bytes for a known much larger source and was not accepted as valid media-transfer evidence. A further comparison was blocked by YouTube's sign-in/bot-verification wall. Probing stopped; no credentials or network workarounds were used. Live YouTube acceleration was therefore not verified in this environment.

The native runtime tests used Android 15 on an x86_64 emulator with 4 KiB pages. The ARM64 APK's signatures, metadata, embedded assets, DEX and ELF alignment were checked, but this update was not executed on a physical ARM64 or Android 16 phone. No universal speed multiplier or error-free operation across every video, network or Android vendor is claimed.

## Build reliability

The optional AGP 8.7.3 resource-path optimization was disabled after it produced an incomplete first ABI resource archive. Complete resources are now packaged in both splits, and the post-build verifier checks every APK's manifest and current bytecode. The verified native payloads and media quality are unchanged by this packaging setting.

Private signing material is kept outside the source tree. GitHub Actions prepares pinned inputs, runs the host/JVM/lint gates, builds both ABIs, and checks the APKs. CI artifacts are explicitly test-signed; the APK supplied in chat uses the original private release identity.
